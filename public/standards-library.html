Web-App Behaviours

Components are what things look like. This is how they should act — the interaction rules that make an app feel fast, honest, and trustworthy even when it's slow, wrong, or offline. Every rule below has a live example: try clicking, typing, and hovering the demos.

13 behaviour standards Demos are interactive — try them

Loading, Not Blank

A blank screen reads as broken. A loading indicator — even a simple one — reads as "working on it." Never let the user stare at nothing.

Don't — blank until ready
Do — show structure immediately
Both boxes take the same ~1.2s to load real content — only the "in-between" experience differs.
1

Never show a blank screen while fetching

Show a skeleton, spinner, or placeholder the instant a request starts — not after a delay.

2

Match the skeleton to the real shape

A skeleton with the right layout (image block, two text lines) sets the right expectation and feels faster.

3

Skip the loader under ~300ms

A spinner that flashes for a frame reads as jank, not speed. Delay showing it by ~300ms for fast responses.

Debounce & Throttle

Don't fire an expensive action on every keystroke, scroll tick, or resize event — wait for the user to pause.

Naive — fires every keystroke
0
API calls
Debounced — fires 400ms after you stop
0
idle
1

Debounce search-as-you-type

~300–500ms after the last keystroke, not on every character.

2

Throttle scroll & resize handlers

Cap expensive layout work to once per animation frame (~16ms), not per event.

3

Cancel stale in-flight requests

If a newer request starts, drop the older one's response so results can't arrive out of order.

Optimistic UI

For actions that almost always succeed, update the interface immediately and reconcile with the server quietly afterward.

Click — the count updates instantly, no spinner, no wait for the server.
1

Update instantly for likely-to-succeed actions

Likes, follows, toggles, reordering — assume success and show it now.

2

Roll back clearly on failure

If the server rejects it, revert the UI and explain why — don't leave it in a false state.

3

Stay pessimistic for high-stakes actions

Payments, permanent deletes, and anything hard to reverse should wait for server confirmation first.

✕ Don't

A clickable row with no hover change and the default arrow cursor — the user has to click blindly to discover it's interactive.

✓ Do

Background shifts, cursor becomes a pointer, and the change happens the instant the mouse arrives — no delay, no fade-in lag.

Prevent Double-Submit

A slow network plus an impatient click equals two orders, two payments, two support tickets. Lock the button the instant it's pressed.

Click it twice, fast — the second click does nothing while the first is in flight.
1

Disable + show loading on the first click

Not after a delay — the instant the click registers.

2

Show a clear success state

Don't just silently re-enable the button — confirm the action landed.

Validation Timing

When errors appear matters as much as what they say.

✕ Don't

Red border and error text appear after every single keystroke, while the user is still mid-word — it feels like being scolded for typing.

✓ Do

Validate on blur (once the user leaves the field) or after a short pause, once they've had a chance to finish.

1

Never clear input on a failed submit

The user should never have to retype a form because one field was wrong.

2

Say what to fix, not just what's wrong

"Needs 8+ characters" beats "Invalid password."

3

Confirm valid fields too

A small checkmark on blur reassures the user as much as an error warns them.

Autosave & Unsaved Changes

The user should never wonder "did that save?" — and never lose work by accident.

All changes saved
1

Show a persistent, quiet "Saved" indicator

If you autosave, prove it — without interrupting the user.

2

Warn before losing unsaved work

If you don't autosave, intercept navigation and browser close with a clear warning.

3

Persist drafts through refresh

A refresh or crash should never wipe out what the user typed.

Preserve State

Nothing erodes trust faster than losing your place — filters reset, scroll jumps to the top, the back button "doesn't work."

Reflect state in the URL
/projects?status=active&sort=date
1

Put filters, tabs, and search in the URL

So the back button, refresh, and sharing a link all just work.

2

Restore scroll position on return

Coming back from a detail page should land where the user left off, not at the top.

3

Remember the last-used view

If a user picks "list view" or "this week," keep it for the rest of the session.

Undo vs. Confirm

Confirmation dialogs interrupt every time, even when the user is sure. Undo lets them act fast and recover if they're wrong.

Q3_summary.pdf
budget_draft.xlsx
meeting_notes.docx
Delete a file — it's removed instantly, with a few seconds to undo.
1

Reversible action → Undo toast

Act immediately, no interruption, with a short window to reverse it.

2

Irreversible action → confirm first

Permanent delete, cancel subscription — use a modal (see Modals in the Component Library).

3

Never use the browser's confirm()

It can't be styled, ignores your design system, and blocks the whole page.

Retry & Offline Handling

Failure is normal — networks drop, servers time out. The app should say so plainly and offer a way forward.

Failed request
✕ Failed to load comments
Offline detection
⚠️ You're offline — changes will sync once you're back online.
1

Every failed fetch gets a visible Retry

Never a dead-end error with no way to try again.

2

Detect offline, say so

Don't leave the user watching a spinner that will never resolve.

3

Queue offline actions

Let the user keep working; sync automatically on reconnect.

4

Write specific error messages

"Card was declined" beats "Something went wrong." Say what happened and what to do next.

Respect Reduced Motion

Some users get motion sickness or distraction from animation. Honor their system setting.

2

Motion should mean something

Use it to show cause and effect (a card expanding into a detail view), never just for decoration.

Keyboard & Focus

Not everyone uses a mouse. Every interaction available by click should be available by keyboard.

1

Full Tab order

Every interactive element reachable by Tab, in a logical, visual order.

2

Enter / Space activate controls

Buttons and custom controls respond to keyboard the same as a click.

3

Esc closes overlays

Modals, drawers, and menus close on Escape, no exceptions.

4

Trap and return focus

Focus stays inside an open modal, then returns to the button that opened it on close.

5

Visible focus, always

Never outline:none without a replacement ring (see Accessibility in the Component Library).
