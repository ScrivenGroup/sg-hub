2. Why the HTML is different (ELI5)

my-site is closer to Word documents on a website. Someone writes a real .html file. The browser downloads that file. CSS on top is Google Material Design 3, hand-rolled. If a page must remember something, JavaScript phones a separate Node backend, which talks to Azure SQL.

The hub is a kit that prints the page when someone visits. You almost never edit an .html file. You edit React pieces (.tsx). Next.js assembles HTML on the server, then React takes over for anything that moves (Gantt, popups, filters). Tailwind is a box of small classes. House colours are a few variables (--ink, --page). A product’s 6-hex code colours the badge only, not the whole page.

3. Future-proof HTML setup

Do not start a third kit (Vue, Svelte, new Vite app, “clean HTML rewrite”). Two stacks is already enough.

Standard for every new product leaf: this hub — Next.js App Router, React, TypeScript, Tailwind, SG tokens, Manrope, existing chrome. Persistence graduates through the same store to Postgres. my-site stays the leaflet island until a leaf is merged here, then that leaflet retires.

Do not unify by rebuilding the hub as static files. Do not rebuild my-site as Next. Two jobs, two front ends, one rule: new capability → hub.

7. Design / layout starting kit

Do not copy my-site MD3. ThemeContract only when a leaf explicitly opts in (e.g. Fuel Tracker dark/car later).

  • Chrome: sticky header, white surface, hairline border. Page ground #F5F5F4, ink #3C3C3B. Manrope. 10px corners. Logo left; optional centred title; actions right.
  • Body: Back/breadcrumbs, then a large heading + colour badge + status pill. Muted description. Cards sg-card. Buttons sg-btn-primary / secondary / ghost (44px tall). Inputs sg-input.
  • Tables: simple HTML or that leaf’s own table CSS. No new table library.
  • Dialogs: never taller than the window; the middle scrolls; footer stays on screen; Esc closes.
  • Colour: 6-hex code → badge only. Traffic-light green / amber / red as already defined.

8. Connect the database

Goal: a Save in Feedback (then other small stores, then MRT) still exists after a zip deploy and after an App Service restage.

Shape: keep one store in the hub. Talk to the existing Azure setting DATABASE_URL (Postgres; hobby Neon — not paid Azure Postgres). Do not add a second database style. MRT guest sandbox is not in the first coding pass.

Phase 0 — you (outside Cursor)

  1. Confirm the Postgres behind DATABASE_URL on app-scrivengroup is the one you want. If stale, replace it in Azure App Settings. Do not paste the string into chat.
  2. Optional: a Neon branch you are willing to wipe while testing.
  3. Be able to az login (needed for zip deploy until Actions exist).
  4. Do not zip-deploy until “stop putting data/ in the zip” ships in the same release as the first DB write.

Cursor cannot log into Neon as you, rotate the URL, or safely print the secret.

Phase 1 — Cursor (no MRT)

  1. Add a Postgres client + Drizzle in this app (not Prisma — that stays on my-site for now).
  2. Tables first: feedback, ideas, notes, changelogs, dependencies, development choices.
  3. If DATABASE_URL is set, use Postgres; on a laptop without it, keep JSON files.
  4. Stop copying data/ into the deploy zip.
  5. Migrate live Azure JSON for those simple files — not the laptop’s small MRT file.
  6. You check Feedback on localhost, say commit, say make it live.
  7. Done: add Feedback on live → deploy or restage again → row still there.

Phase 2 — Cursor (MRT, later session)

  1. Design before code: live plan in Postgres (maybe one JSON blob at first); share passwords as rows; sandbox = two desks still, but not zip-wiped files; activity log in DB.
  2. Migrate the live ~427 KB MRT file from Azure, not the laptop 3-dam copy.
  3. Stop the “fewer than 20 dams → wipe hours” rewrite against production.
  4. Done: Save on live Gantt → zip deploy → hours still there; guest password still works without recreating audiences.

Order: simple registers → zip exclude → migrate those files → then MRT. Sequential. One session per phase.

10. Great Merging of ’26

Move my-site web-apps and their data into this hub. Cursor implements here. Claude (or you) exports. This is not a git merge of two histories. Static HTML and Next do not fast-forward into one repo.

Each my-site app becomes a hub leaf (a card on a floor) with SG chrome and the hub store. my-site then shows a stub or removes the page.

How to get source in front of Cursor

Preferred: clone my-site as a sibling folder, e.g. C:\1D\Anyliki\Scriven Group - Documents\Cursor\my-site, and tell Cursor that path. Do not nest it inside the hub repo.

Also fine: a zip of Prisma schema, app folders, and JSON/CSV data with no secrets.

Not useful: “Claude, describe the apps” with no files.

Paste this to the Claude / my-site session

We are merging my-site products into the ScrivenGroup Next.js hub (Cursor repo).
Please do not rewrite them as hub code.

Give me a single pack:
1. Inventory table: app name, folder path, URL on my-site, what it stores (tables or localStorage), who uses it.
2. prisma/schema.prisma (or equivalent) and which tables belong to which app.
3. A JSON or CSV export of those tables (no connection strings, no API keys, no Entra secrets).
4. For each app: entry HTML/JS files and any shared CSS that is not just MD3 chrome.
5. Anything that must keep working (auth assumptions, unguessable share links, cron, cold-start pings).
6. Confirm: after Cursor ports an app, we will stop changing that app on my-site.

Do not start a second Next.js app. The hub already exists.

Suggested order

  1. Inventory from the pack.
  2. Hub DB cutover for simple hub stores first, so new leaves are not born on JSON-in-wwwroot.
  3. Port the smallest my-site app as sketched → building.
  4. Load exported data into hub types.
  5. You review localhost → commit → live.
  6. Repeat. MRT is already on the hub — do not “merge MRT from my-site.”
  7. When a leaf is live here, Claude archives it on my-site.

Cursor will not rewrite MRT as vanilla HTML, will not add Azure SQL as a second hub ORM unless you later lock that, and will not merge git remotes. One leaf per session.
