How you use The Doing

Ops guide
28 Aug 2026 · rev B

Your use case: open Cursor → ask for something that might touch many hats and many environments. You should almost never touch folders yourself. Front desk is usually in Plan mode. One primary session decides; workers do jobs and report back. The pack is Cursor’s brain — including zip & go to another machine from chat only.

Hard rule for you: talk to Front desk. Don’t create folders, rename trees, or “just tidy the disk.” That is Janitor / Front desk work. Your job is wishes + decisions.

Brain pack does

  • Remembers the school rules
  • Holds the board + tickets
  • Forces intake behaviour
  • Owns housekeeping history
  • Travels to a new PC with you

Brain pack does not

  • Replace a Thing’s own code rules (e.g. ScrivenGroup PLATFORM.md)
  • Store giant build artifacts
  • Be edited by hand as a hobby
  • Invent status the board doesn’t have

Future-proof trick: Things can come and go. The brain pack stays. A new computer = copy/clone the brain pack + open it → you’re pre-organised before the next Thing exists.

2. How you use it day to day

You open the brain pack as the Cursor workspace (not a random subfolder), then you talk. For Front desk, prefer Plan mode (not always — but default when steering).

1. OpenOpen cursor-brain (or campus root that includes it + Things).
2. AskPlain wish in Plan mode when steering.
3. IntakeFront desk only. Reads handbook + board + PRIMARY.
4. Plan by hatsAmbiguous wishes → options per hat. You pick.
5. DispatchWorker chats get tickets. They report back; they don’t re-boss.

Plan mode must shape results as role-tickets

3. One primary boss — no session fights

Every new chat can feel like “I’m in charge now.” That causes fights: Session A decides X, Session B undoes X. We kill that with an authority ladder.

Who may decide

  1. You — intent, priorities, locks
  2. Primary session — Front desk (usually Plan). Writes tickets + board. Owns the thread of work.
  3. Board / locked files — beat any worker opinion

Who may only do + report

  • Worker sessions — Builder / Janitor / Reviewer
  • Execute one ticket
  • Write a report back (tickets/reports/ + board update)
  • Escalate blockers to Primary — never invent a new plan of record
RuleMeaning
Primary is named doing/board/PRIMARY.md says which Front desk thread is live. Workers read it.
Workers are not bosses A Builder must not rewrite campus structure, rename words, or open rival tickets “while here.”
Disagreement → board, not debate If two sessions conflict, board + Primary win. Loser becomes a Janitor harvest or a new ticket proposal for Primary.
Report shape Worker ends with: done / blocked · files touched · board rows updated · questions for Primary (not new doctrine).
Sub-agents Errands inside one worker ticket. They die at the bell. They never become a second Primary.
Iron rule: Sub-sessions do the job and report back to the primary Front desk session. They do not become the next new boss. If they need a decision, they stop and escalate.

When a worker chat starts

  • Paste / open the ticket file (law for this sitting).
  • Read PRIMARY + board row + Thing handbook if building.
  • Do only the ticket. No “while we’re here” doctrine.
  • Write report → update board → stop. Primary (or you) continues the story.

5. Consistency in The Thing (design, icons, standards)

You guide intent / structure / function. Agents bring craft from a world of knowledge — but craft must land in locked files, or every Builder reinvents the look.

You lock

  • What the Thing is for
  • Structure (hubs, flows, what’s in/out)
  • Function requirements
  • Design intent (“calm”, “dense data”, “playful map”)
  • Which proposed standard wins when options are shown

Agents propose & implement

  • Best-practice patterns, a11y, layout systems
  • Icon set candidates, type scale, tokens
  • Component conventions
  • Write them into STANDARDS.md / design tokens
  • Builders obey locks; they don’t “improve” by silent drift
LayerWhere it livesHow it stays consistent
Intent Thing DESIGN.md (short, human-locked) Front desk asks before changing intent
Standards Thing STANDARDS.md + tokens/code Agent proposes → you lock → Builders must match
Template seed Brain templates/new-thing/ New worlds start with empty-but-shaped DESIGN/STANDARDS stubs
Review Reviewer hat ticket “Does this match STANDARDS?” yes/no — not a redesign cosplay

Agents can have the best ideas — that’s the point. The ritual is: propose → you lock → implement against the lock. Without the middle step, “best ideas” become session fights again.

6. Future-proofing + zip & go

  • Stable words — never rename Product / Ticket / Board / Hat / Temp for fun.
  • Brain ≠ Thing — product code never becomes the only place rules live.
  • Board schema stays boring — add columns rarely; prefer new ticket types over clever formats.
  • Template for new Things — birthing a world is a ticket using templates/new-thing, not a vibe folder.
  • Authority files travel with the pack — PRIMARY, AUTHORITY, PLAN-SHAPE are part of the brain.
  • Version the ritual, not the lore — housekeeping log records moves so future-you knows why.

Zip & go (zero Explorer — chat only)

Goal: on machine A you type one prompt; on machine B you paste one prompt. No manual zip UI, no “now open this folder and click…” beyond opening Cursor once.

MachineYou type in chatAgent does
A · Export Zip and go Follow doing/portable/EXPORT.md: freeze board note · package cursor-brain (and optional Thing list) into a single archive in a known path · print a short Import prompt you can copy
B · Import Paste the Import prompt (from EXPORT) into a fresh Cursor chat Follow IMPORT.md: unpack · verify handbook/rules · set PRIMARY · open Mission Control summary · ask “ready for a new Thing?” — still no human disk tourism

Getting the archive across machines (USB, cloud, email) is the only physics problem. Ideal agent behaviour: produce the file + the pasteable prompt; you only move the file if the agent can’t reach cloud. Prefer: agent uploads/downloads when credentials exist; otherwise one drag of a single zip is the maximum human disk touch — never a tree tour.

New Thing on the new machine

  1. Import finishes (brain alive).
  2. You say: “Start a new Thing called ___ using the template.”
  3. Front desk (Plan) tickets it · Builder materialises from templates/new-thing · board gains a world row.

  • Are five words still stable?
  • Any tickets older than N days? park / kill / split
  • Any Thing folders not on THINGS.md? register or quarantine
  • Any board rows with no home on disk? fix or park

  • Update mudmap “you are here” + housekeeping LOG
  • No surprise reorg — propose tree diff first; you approve; then execute
